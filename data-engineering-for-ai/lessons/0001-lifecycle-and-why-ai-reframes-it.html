Unit A · Foundations — Lesson A1

Data doesn't arrive AI-ready. Someone has to move it there.

Before an agent can retrieve "the renewal terms for Acme," a long, unglamorous pipeline had to run first. This lesson is the map of that pipeline — and why "for AI" changes what counts as done.

Your goal in this course is to take all of an organization's data and get it to the point where an agent can find the right slice of it and be trusted to act on it. That end state has a name people started using in 2025–26: AI-ready data — data that's been described and governed well enough that a model can retrieve exactly the right thing and you'd trust the result. The striking part is how rare it is. As of Mar 2026, only 7% of enterprises say their data is completely ready for AI.[3] Not 7% have adopted AI — 7% have the data ready. The other 93% is the work this course is about.

To see why that gap is so wide, you need the map of how data gets anywhere at all.

What "data engineering" actually is

Data engineering is the discipline of building the systems that move data from where it's produced to where it's used — reliably, and at the right quality. It's a distinct job from data science (building models) and data analysis (interpreting results): data engineering is the plumbing and the warehousing underneath both. If the data scientist is a chef, the data engineer stocks the kitchen — sourcing, cleaning, labelling, and shelving every ingredient so the right one is within reach when needed.[2]

The data engineering lifecycle — the backbone of the whole course

The most widely-used mental model comes from Joe Reis & Matt Housley's Fundamentals of Data Engineering: data flows through five stages, from raw production to useful delivery.[1] Read it top to bottom — each stage feeds the next.

1 · GENERATION
Where data is born: an app writes a row, a user files a ticket, a contract is signed. You usually don't control these source systems — you receive from them.
2 · STORAGE
Where it lands and lives. Not one place — databases, warehouses, lakes (Unit A3). Storage underpins every other stage, so it's both a stage and a constant.
3 · INGESTION
Moving it in from source systems — batches on a schedule, or streams in real time. Often the hardest, most brittle part in practice.
4 · TRANSFORMATION
Turning raw into useful: cleaning, joining, reshaping, computing. Raw data is rarely usable as-is; this is where it earns its keep.
5 · SERVING
Delivering it to whoever uses it — a dashboard, an analyst, an ML model, or (our case) an agent. Data has no value until it's served for a purpose.

Running underneath all five stages are the undercurrents — concerns that don't sit at one stage but cut across every one: security, data management (governance), DataOps, data architecture, orchestration, and software engineering.[1] Hold onto this word. Most of what makes data AI-ready — describing it, governing it — lives in the undercurrents, not the five visible stages. Units B and C of this course are essentially "take two undercurrents and make them the main event."

the reframe: what changes when it's "for AI" The five stages are decades old — they're how a 2010 sales dashboard got built too. What changed is the serving target and, with it, the bar for the undercurrents. A dashboard serves a human who brings their own judgment, ignores a weird row, and knows Acme is the same as "Acme Corp." An agent brings none of that. It will confidently act on the weird row, treat "Acme" and "Acme Corp" as two customers, and expose data it was never meant to touch — unless the description and governance undercurrents did their job upstream. Same pipeline; far less tolerance for a sloppy one.

How much does closing that gap matter? A concrete, dated data point: OpenAI's own engineering team published its internal data-agent design in Jan 2026. Time to answer a complex business question dropped from over 22 minutes to 1 minute 22 seconds — not by changing the model, but by putting a full "context stack" (governed definitions, entity resolution, lineage) underneath it.[3] The data engineering, not the model, was the bottleneck.

Meet Meridian — the company we'll build for

Concepts stick when they have something to hold onto, so one example company runs through every lesson. Meridian is a mid-size B2B SaaS business (fictional, but realistically messy). Its data is deliberately varied, because yours will be too:

KindMeridian's dataWhy it's here
StructuredPostgres app DB (customers, subscriptions, invoices); a CRM (accounts, deals)The "systems of record" — authoritative, schema'd, familiar to you as an engineer
Semi-structuredSupport tickets; JSON event & API logsSelf-describing but irregular — the awkward middle
UnstructuredProduct wiki; Slack history; signed-contract PDFs; sales-call transcriptsNo schema at all — the pile traditional analytics ignored, and exactly where AI earns its keep

We'll follow one signed-contract PDF as a recurring thread — call it the Acme contract. Watch what it takes for an agent to safely answer "what are Acme's renewal terms?" It has to be stored somewhere it can be found (Unit A), described so the system knows it's a contract for Acme signed on a date (Unit B), governed so only permitted callers see it (Unit C), made reachable to the model as retrievable text (Unit D), and finally acted on by an agent that quotes the right clause (Unit E). That path — store → describe → govern → make reachable → act on — is the spine of this course.

the spine store → describe → govern → make reachable → act on. Each unit owns one segment; the Acme contract travels all of them. If you ever feel lost in a later lesson, ask which segment you're in — the answer re-orients everything.

Check it sticks

① From memory: name the five stages of the data engineering lifecycle in order, and say what the "undercurrents" are — and why this course cares about them more than the stages.

Stages: generation → storage → ingestion → transformation → serving. Undercurrents: cross-cutting concerns that run under every stage — security, data management/governance, DataOps, data architecture, orchestration, software engineering. This course cares about them most because "AI-ready" is won or lost in the describe and govern undercurrents, not in the five visible stages — an agent, unlike a human, has no judgment to compensate for weak ones.

② A team upgrades from a human dashboard to an AI agent over the very same pipeline. Which single change best explains why the agent needs far more of the pipeline to be right?

It's the loss of human judgment. A person ignores a weird row, reconciles "Acme"/"Acme Corp," and won't open data they know is off-limits. An agent does none of that unless description and governance handled it upstream — so the same pipeline now needs its undercurrents to actually be right. (Speed is real but not the reason; vector DBs and the structured/unstructured claims are just false as stated.)
