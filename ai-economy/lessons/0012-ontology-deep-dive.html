UNIT B · THE TECHNOLOGY STACK — LESSON 0012

Ontology, taken apart

B3 introduced ontology lightly. This time: the actual mechanics, the real critique, and the open-source alternative for the governance problem it's solving.

Palantir's Ontology, piece by piece

Palantir's own docs split the Ontology into two families: semantic elements, which describe structure, and kinetic elements, which enable change.[1]

ElementFamilyWhat it is
Object TypeSemanticAn entity or event in the organization — e.g. "Vehicle," "Employee," "Shipment."
PropertySemanticAn Object Type's characteristics/attributes.
Link TypeSemanticA relationship between two Object Types.
Action TypeKineticThe schema for a bounded, permissioned set of edits (plus side effects) that a human or an agent can submit.
FunctionKineticServer-side code, run inside Foundry's governed execution environment, that reads properties, traverses links, and makes edits.
how an agent actually *acts*, not just queries The governance boundary sits at the Action Type level. An agent given access to an Ontology isn't handed open-ended write access to the underlying data — it's scoped to a specific, pre-defined, auditable set of Action Types. "This agent may submit Action X on Object Type Y" is the actual permission being granted, not "this agent may edit anything." That's the mechanism behind Palantir's claim of governed agent autonomy, not a vague promise.

Ontology MCP is the bridge to the rest of the ecosystem from B4: a Developer Console feature that exposes an application's Ontology resources as MCP tools, so external agents (Claude, Copilot Studio, Gemini Enterprise) can act as MCP clients against it. It exposes exactly three tool classes — read objects, execute pre-approved actions, query data — and the scope is configured per-application by an admin, so an external agent only ever sees the slice an admin explicitly opened up.[2]

The skeptic's case

There's a real, pointed critique here, not just marketing pushback. A February 2026 piece, "Palantir's 'Ontology' Hustle," makes the sharpest version of it plainly: Object Type = table, Property = column, Link Type = foreign key, Action = stored procedure — i.e., this is entity-relationship modeling, a technique Peter Chen formalized in 1976, wearing a philosophy-department word. The argument is that the term's main function is to make people unfamiliar with databases believe they're looking at something new.[3] This isn't a fringe take — a follow-up public debate on the claim reportedly landed 75% of the audience on the critic's side, real traction among data-infrastructure practitioners.[4]

The fair counterpoint: the genuinely hard, valuable part may not be the vocabulary at all, but the governance/permissioning layer around Actions, plus the hands-on work of actually curating an ontology for one organization's messy real-world data (Palantir's "forward-deployed engineer" practice — A5 covers how that role has since spread industry-wide). Whether "ontology" the word is doing real technical work, or just branding on top of familiar database primitives, is a separate question from whether the product is useful.

teaching takeaway Treat "Ontology" as Palantir's product name for a governed semantic layer + write-permission layer, built on conventional data-modeling primitives (entity-relationship modeling + scoped write permissions + an MCP-exposed API surface). Useful to know as a concrete pattern. But recognize both the mechanics and the critique when the term comes up — using it uncritically as if it were self-evidently novel is a small tell.

Governing what agents can do — the open, non-proprietary version

Action Types are Palantir's proprietary answer to a general problem: how do you let an agent take real actions while keeping it inside a bounded, auditable permission set? Two open policy-as-code engines solve the same problem without a platform lock-in.

OPA (Open Policy Agent) is a CNCF-graduated policy engine (graduated January 2021) using its own language, Rego, originally built for use cases like Kubernetes admission control and API-gateway authorization. The 2025-2026 pattern for agents: OPA runs as a sidecar in front of an agent's tool-call gateway — before every tool invocation, the agent runtime queries OPA with the principal, the tool, and the arguments, and OPA returns an allow/deny decision (plus reasoning) in sub-millisecond time, with every decision streamed to a SIEM for audit.[5] The logic: even if a prompt-injected or hijacked agent decides to do something disallowed, it can't actually execute it, because authorization lives entirely outside the model's own control. This pattern is getting real attention now partly because the OWASP Top 10 for Agentic Applications (2026) names "Agent Goal Hijacking" as its top risk.

don't trust stale knowledge — OPA had a real shock In August 2025, Apple hired away OPA's core maintainer team from Styra (the company that commercialized OPA) — Teemu Koponen, Torin Sandall, and Tim Hinrichs among them — without formally acquiring Styra itself. Styra appears to have shut down; as part of the wind-down, its commercial tools (Enterprise OPA, OPA Control Plane, the Regal linter) were released as open source. The CNCF retains formal control of the OPA project itself, which continues as community-maintained.[6] Anyone still picturing "OPA, made by Styra" is working from a picture that stopped being accurate in the second half of 2025 — a clean example of exactly the kind of shift this course keeps warning about.

Cedar is AWS's own open-source policy language (Apache 2.0, 2023), powering Amazon Verified Permissions. It joined the CNCF too — as a Sandbox-maturity project (the earliest tier) in October 2025, meaning Cedar and OPA are now both CNCF projects, just at very different maturity levels.[7] Cedar's flagship 2026 agent use case is AWS's own: Amazon Bedrock AgentCore integrated Cedar-based policy, reaching general availability March 3, 2026, letting teams attach deterministic Cedar policies to a Bedrock AgentCore Gateway to govern exactly what tools an agent can reach. AWS's stated rationale for Cedar specifically: it's formally verified and analyzable (built on automated reasoning, so policy conflicts are detectable, not just pattern-matched), evaluates in bounded time for predictable low-latency decisions in an agent's live tool-call path, and uses human-readable syntax meant to be legible to compliance staff, not just engineers.

OPA vs. Cedar for agent governance — current discourse, not a settled benchmark No rigorous, vendor-neutral benchmark comparing the two for this specific use case was found — what exists is qualitative industry commentary treating "OPA with Rego, or AWS Cedar" as the two most-cited choices for the agent-gateway policy-decision-point pattern. The rough positioning: Cedar pitches formal verifiability and analyzability; OPA pitches ecosystem maturity, broader existing deployment, and Rego's more flexible general-purpose data-joining. Treat any confident "X is just better" claim about this pair with the same skepticism A7 taught for funding numbers — this is live, evolving discourse, not measured fact.

Check it sticks

① In Palantir's Ontology, what's the difference between the semantic elements and the kinetic elements?

Semantic elements describe structure: Object Types (entities/events), Properties (attributes), Link Types (relationships). Kinetic elements enable change: Action Types (schema for a bounded, permissioned set of edits an agent or human can submit) and Functions (server-side code that reads/traverses/edits via the governed execution environment).

② What's the skeptic's one-line mapping of Ontology terms onto plain old database terms — and what's the argument behind it?

Object Type = table, Property = column, Link Type = foreign key, Action = stored procedure. The argument: this is 1976-era entity-relationship modeling wearing new, philosophy-flavored branding — the word's main effect is making it look novel to people unfamiliar with databases.

③ Why does OPA run as a sidecar in front of an agent's tool-call gateway, rather than trusting the agent/model itself to decide what's allowed?

The whole point of the pattern is that the agent's own "decision" to do something is never trusted as the final word — a hijacked or manipulated agent might decide to do something harmful, but it physically cannot execute it if the authorization check sits in an independent system outside the model's control.
