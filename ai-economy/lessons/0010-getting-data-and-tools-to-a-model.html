How a model reaches the world beyond its training data

B2 covered how trustworthy data gets built. This lesson is the next layer up: how a model actually gets that data, and the tools around it, at query time.

MCP — the connector every agent now speaks

Model Context Protocol (MCP) is an open standard for connecting a model to external tools and data sources through one common interface, instead of every app writing its own bespoke integration for every tool. The common analogy is "USB-C for AI" — one physical connector, many devices.[1]

Anthropic created and announced MCP in November 2024. What matters for "is this current" purposes: in December 2025, Anthropic donated MCP to the Agentic AI Foundation, a new directed fund under the Linux Foundation, co-founded alongside Block and OpenAI — meaning MCP is no longer an Anthropic-only protocol, it's cross-vendor, neutrally governed infrastructure.[2] Adoption is real and large: 97M+ monthly SDK downloads and 10,000+ active MCP servers in production.[3] Of everything in this unit, MCP is the term you can treat as settled, not in flux — and you already saw it show up again in B2 as the connective layer for dbt Agents.

RAG vs. long-context vs. fine-tuning

For about two years, the prediction was "context windows will keep growing until RAG (retrieval-augmented generation — fetching relevant documents and feeding them to the model at query time) becomes unnecessary." 2026 evidence says the opposite: a controlled comparison found brute-force long-context lost to RAG at scale — up to ~24x more expensive, and prone to losing facts before even hitting its advertised limit.[4]

The current working division of labor: fine-tuning changes how a model behaves (tone, format, task shape) — it's a poor tool for facts that change often. RAG supplies current, citable facts, and wins whenever the underlying data changes faster than the model gets retrained. Long-context is genuinely useful for one-off, whole-document reasoning — not as a RAG replacement at scale. Treat the three as complementary layers of one system, not competing techniques.

a RAG variant worth naming precisely: GraphRAG Standard RAG retrieves by similarity (vector search). GraphRAG retrieves by traversing relationships in a knowledge graph instead — better suited to multi-hop questions ("who reports to the person who approved this vendor's last contract?") that vector search handles poorly. Be precise about which "GraphRAG" you mean: Microsoft GraphRAG is a specific research technique (LLM-extracted entity/relationship graph, clustered via Leiden community detection, with hierarchical summaries). neo4j-graphrag is Neo4j's own, simpler, first-party package — Cypher graph queries plus text-chunk retrieval, not a reimplementation of Microsoft's method. A separate, explicitly experimental community project (ms-graphrag-neo4j) does reimplement Microsoft's specific technique using Neo4j as the backing store — but that's a distinct bridge project, not what "neo4j-graphrag" means by default. The one-line rule: GraphRAG is a retrieval pattern, not a single product — you can implement it on Neo4j, Postgres, or a custom graph engine.[5] Adoption is real but still a minority approach — under 15% of enterprises had graph-based retrieval in production as of 2025 — though intent to adopt hybrid vector-plus-graph retrieval tripled in a single quarter of 2026 (10.3% to 33.3%). The 2026 direction is hybrid, not graph replacing vector.

Ontology — a first pass

"Ontology" has two live meanings right now, and mixing them up is an easy tell that someone hasn't caught up with 2025–2026 usage. The classical sense, from knowledge representation and the semantic web, is a formal specification of the concepts, properties, and relationships in a domain (think RDF/OWL). The newer enterprise-AI sense, popularized specifically by Palantir, is a governed semantic layer sitting on top of an organization's raw data — every noun, relationship, rule, and permission modeled as a queryable, actionable object that AI agents act on directly instead of touching raw unstructured data.[6] If you hear "ontology" in an AI-agent conversation in 2026, assume the Palantir-flavored sense unless context says otherwise. This is deliberately just the surface — B5 opens the actual mechanics and the real critique of this term.

Check it sticks

① What problem does MCP solve, and why is it safe to treat as "settled" rather than "in flux"?

It gives models one common interface for connecting to external tools/data instead of a bespoke integration per tool. It's settled because Anthropic donated it to the Linux Foundation's Agentic AI Foundation (co-founded with Block and OpenAI) in Dec 2025 — it's now cross-vendor governed infrastructure with large real adoption, not a single company's proprietary protocol.

② You need a support bot to answer questions from a knowledge base that gets updated daily. Which approach fits best?

Fine-tuning is the worst fit for facts that change often — you'd be constantly retraining. Long-context works but loses on cost (up to ~24x more expensive at scale) and can drop facts before hitting its limit. RAG is built exactly for data that changes faster than a model gets retrained.

③ Is "neo4j-graphrag" the same thing as "Microsoft GraphRAG" running on a Neo4j database?

Neo4j's first-party neo4j-graphrag package uses Cypher queries plus text-chunk retrieval, not Microsoft's Leiden-clustering method. A separate, explicitly experimental community project (ms-graphrag-neo4j) does reimplement Microsoft's specific technique on Neo4j — but that's a distinct bridge, not what neo4j-graphrag means by default.
