Unit C・Twentyへの実装 — レッスン C1（Unit C 開始）

データモデルの心臓部

Unit A・Bを通して、Twentyの奇妙な挙動——標準機能の少なさ、Group Byの制約、Ownerの単一性、複数Dashboard——に何度も出会ってきた。それらはバラバラの制約ではなく、1つの設計に由来する。C1ではその設計そのものを見る。

なぜTwentyはこう動くのか — メタデータが実行時にAPIを生む

A2で「プラットフォームであり製品ではない」という思想を紹介したとき、その根拠はTwenty自身の言葉だけだった。ここで、その言葉が指す技術的な実体を見る。Twentyのデータモデルは、コードとして書かれていない——メタデータ（metadata）としてデータベースに保存されており、GraphQL API自体がそのメタデータから実行時に組み立てられる。[1]

具体的にはこうだ——CompaniesやOpportunitiesのようなオブジェクト、そこに属するフィールドの定義は、Twenty内部の管理用データベースの中にデータそのものとして保存されている。ユーザーが管理画面でカスタムオブジェクトを作ると、そのメタデータを読み取ってGraphQLのスキーマ（型・クエリ・フィルタ・並び替え）が自動的に生成される——「UIでカスタムオブジェクトを定義すると、数秒後にはAPI上に対応する検索クエリが現れる」という速さで完結する。[1] Salesforceのような従来型の製品でカスタムオブジェクトを作る場合と違い、コードを書いてデプロイする工程が丸ごと存在しない。

なぜこれが「プラットフォーム」の正体なのか A2で見た「Lead専用の機能は作らない、汎用的な部品を足す」という設計判断は、精神論ではなくこの仕組みの直接の帰結だ——Twenty自身の開発チームにとっても、Lead用の特別なコードを書くのと、ユーザーが自分でカスタムオブジェクトを定義するのとでは、後者の方が本質的に軽い。オブジェクト・フィールドがデータとして存在する以上、「新しい概念を追加する」という行為が、開発チームにとってもユーザーにとっても同じ操作（メタデータの追加）になる。この対称性が、Twentyが機能を製品側に焼き込みたがらない理由の技術的な土台だ。

マルチテナントの仕組みもこの延長線上にある——契約する組織（B2で見たWorkspace）ごとに、独立したPostgreSQLのスキーマ（データベース内の名前空間）が割り当てられる。[1] あるWorkspaceでカスタムオブジェクトを作っても、他のWorkspaceには一切影響しない——スキーマそのものが分離されているからだ。

フィールドの全体像 — A1で見た型はごく一部だった

A1〜B6では、Select・Number・Currency・Date・Relationといった型を場当たり的に使ってきた。Twentyのフィールド型は、公式ドキュメントに載っているものだけで以下がある。[2]

Text1行のテキスト
Long Text複数行のテキスト
Number整数・小数
Currency通貨コード付きの金額
Boolean真偽値（チェックボックス）

Select／Multi-Selectあらかじめ決めた選択肢から単一選択／複数選択
Relation他オブジェクトのレコードへのリンク
Email／Phoneメールアドレス／電話番号（主＋複数の追加値に対応）

Rating星評価（1〜5）

JSON構造化されたJSONデータ

この一覧を見ると、B1・B2で出てきた制約が、単発のルールではなく「Group ByはView（見せ方）によって対応する型が違う」という一貫した事実から来ているとわかる——Table ViewのGroup ByはSelect field限定（だからB1は「セグメントの軸はSelect fieldに」と言った）。Dashboard ChartのGroup ByはSelect field・日付・Relationに対応する（だからB2はOwnerというRelationフィールドをDashboard側に持ち込んだ）。同じ「Group By」という名前でも、置き場所によって使える型の範囲が違う——これを知らずにTable ViewでOwnerをグループ化しようとすると、そこで初めて壁にぶつかる。A1の「単なる属性はフィールドで」という判断も、この型カタログのどれを選ぶかという話に還元される。

リレーションの全体像 — 3つのカーディナリティと接合オブジェクト

A3で紹介したCompany → Peopleという例は、実はOne-to-Many（1つのCompanyに複数のPeople）の一例でしかなかった。Twentyのリレーションには3つのカーディナリティ（対応関係の型）がある——One-to-Many（1つのCompanyに複数のPeopleが所属）、Many-to-One（複数のPeopleが1つのCompanyに所属、同じ関係を逆から見た形）、Many-to-Many（両側が複数対複数で結びつく）。[3]

Many-to-Manyの実装は、A3で見た中間オブジェクト（ジャンクションオブジェクト）そのものだ——2つのオブジェクトの間に、関係そのものを表す第三のオブジェクトを挟む。[3] Twentyには、この中間オブジェクトをUI上から隠し、あたかも直接繋がっているかのように最終的な関連レコードだけを表示するJunction Relationという機能もある——ただし執筆時点ではベータ機能で、設定から有効化する必要がある。[3] A3で「Role（役割）を中間オブジェクトの属性として持たせる」と設計したときの、まさにその仕組みの正式名称がこれだった。

リレーションを作る手順 Settings → Data Model → 起点となるオブジェクトを選択 → 「+ New field」→ Relationを選択 → 対象オブジェクトを指定 → 起点・対象それぞれのフィールド名とカーディナリティを設定 → 保存。[3] 1つ実務上の注意点——複数のオブジェクト型を指す（ポリモーフィックな）Relationは、現時点でCSVのインポート・エクスポートに対応していない。[3]

カスタムオブジェクトを作る — 実際の手順

Settings → Data Model → 「+ New object」→ 単数形・複数形の名前（例：listing／listings）とアイコン、説明文を入力 → 保存。[4] これだけでオブジェクトはサイドバーに現れ、即座にレコードを追加できるようになる——冒頭で見た「メタデータを足すだけでAPIが生える」という仕組みが、この操作の裏側で起きていることそのものだ。

誰が触れるか — 権限の3層

ここまでは「何を作れるか」だった。最後に「誰がそれに触れるか」——Twentyの権限システムは3層で構成される。[5]

層制御するもの
ロール（Role）組織構造に応じたカスタムロールを作り、権限をまとめて割り当てる
オブジェクト権限あるオブジェクトのレコードを閲覧・編集・削除できるかどうか
フィールド権限オブジェクト権限の上に重ねる、より細かい制御——特定のフィールド（機密情報等）だけ閲覧・編集を制限する

これはB6のダッシュボード3層設計（担当者／マネージャー／経営層）とも噛み合う——B6で「誰が何を見るべきか」を情報設計として決めたなら、権限システムはそれを実際にアクセス制御として強制する層になる。A3の合議体のうち機密度が高い情報（Procurement/Legalが握る契約条件・ベンダーリスクの詳細等）を、フィールド権限で担当者以外に見せない、といった設計もここで可能になる。

理解を確認する

① 記憶から答える：Twentyでカスタムオブジェクトを作るとき、コードのデプロイが不要なのはなぜか。この仕組みが、A2で見た「プラットフォームであり製品ではない」という思想とどう繋がるか。

Twentyのオブジェクト・フィールド定義はコードではなくメタデータとしてデータベースに保存されており、GraphQL APIはそのメタデータから実行時に生成される。ユーザーがUIでカスタムオブジェクトを定義すると、対応するAPIクエリが数秒で使えるようになる——コードを書いてデプロイする工程が存在しない。これにより「新しい概念を追加する」操作が、開発チームにとってもユーザーにとっても同じ（メタデータの追加）になり、Twentyが特定の業務プロセス専用の機能を製品に焼き込みたがらない、という設計判断の技術的な土台になっている。

② あるOpportunityに複数の社内担当者（AE・技術サポート・カスタマーサクセス）を紐づけ、それぞれの役割も記録したい。B2・A3で扱ったこの問題を、C1で学んだ用語で正確に言い直すとどれか？

「1つの案件に複数の人、それぞれに役割」という構造は、両側が複数対複数になりうるMany-to-Manyの関係で、Roleという情報は関係そのものに属する属性——A3で見た中間オブジェクトのパターンに正確に一致する（c）。One-to-Many（a）は片側しか複数になれない。Multi-Select（b）は選択肢の列挙であって、関連レコードへのリンクではない。Ownerフィールドの複製（d）は場当たり的で、役割の種類が増えるたびにフィールドを増やす羽目になる。

③ 記憶から答える：Twentyの権限システムの3層を挙げ、それぞれ何を制御するか説明してください。
