コースマップ

3ユニット構成のシラバス全体。Unit A（案件管理の基礎＝背骨）→ Unit B（経営指標）→ Unit C（Twentyへの実装）の順に積み上がる。Bの各指標はAの背骨データに依存し、Cはそれを実際のTwenty設定に落とし込む。現在地より先の枠は計画中で、進み方に応じて内容が変わる。

貫く一本の流れ ひとつの案件が、リードとして生まれ（A）、クオリフィケーションを経て正式な商談になり（A）、パイプラインステージを進み（A）、受注か失注で終わる（A）。この一連の記録の集計が経営指標（B）になり、最終的にTwentyのオブジェクト・フィールドとして実装される（C）。どのレッスンも、この流れのどこかの区間を担当する。
Unit A — 案件管理の基礎（背骨）
A1 done 商談の背骨：リードから受注／失注まで リード／クオリフィケーション（BANT・MEDDIC）／案件／パイプラインステージ／4つのV／失注理由。TwentyのOpportunitiesオブジェクトとの対応も導入。
A2 done 「見込み客」と「案件」のあいだ SDR/AEの分業とBANT/MEDDICの実運用。TwentyにはSalesforceのようなLeadオブジェクト／Lead Convertが無く、Personに新規Opportunityを紐づける運用でカバーする、という決定的な設計差。加えて「platform vs product」という設計思想と、そのコスト。
A3 done 「一人」ではなく「合議体」を管理する 購買委員会（6役割）とアカウント階層。役割（Role）は関係そのものの属性——中間オブジェクトでモデリングする、というA1原則の応用形。
A4 done 案件の「外側」— 活動記録とERPとの境界線 活動記録は着地予測の先行指標。TwentyのTask/Note＋メール・カレンダー連携（People/Companies/Opportunities限定）＋Timeline。Quote-to-Cashの原則とTwenty内に作り込むか外部連携かの判断。Unit A完走。
Unit B — 経営指標
B1done 案件を「切る」— セグメント分析 仮説駆動（データ無し）→実データ駆動（受注/失注/チャーンを揃える）→定期見直し、というループ。ファーモグラフィック5軸。TwentyのSelect field＋Group By、規模が大きくなればDashboardへ。
B2done 誰が「効いて」いるか — メンバー別生産性・効率 アクティビティ指標とアウトカム指標。クオータ達成率。OwnerはSelect fieldでなくリレーションなので、メンバー別集計は最初からDashboardへ——B1の制約の応用形。Task件数は稼働管理にはならない。
B3done 失注は「消えたデータ」ではない 失注理由は症状であり原因ではない（営業担当の6割が誤認）。停滞案件という第三の終端。機会損失額の集計とTwentyでの停滞検知ワークフロー・滞留日数追跡。
B4done 着地予測 フォーキャストカテゴリとステージ確度は別軸。確度は実測すべき（設定値ではない）。B3の停滞検知が予測のかさ上げを防ぐ前段フィルタになる。TwentyはProbability/Expected Amount/フォーキャストカテゴリすべて自作。
B5now 季節性とYoY比較 3年チャートでの季節性発見、B2B特有の要因（期末予算消化等）。移動祝日（イースター例）がYoY比較を壊す。Twentyの「Month of year」粒度で年をまたいで束ねる。
B6planned ダッシュボード設計としてまとめる B1〜B5をひとつの経営ダッシュボードにどう構成するか。誰が何を、どの頻度で見るか。
Unit C — Twentyへの実装
C1planned Twentyのデータモデル基礎 標準オブジェクト／カスタムオブジェクト／フィールド／リレーションの全体像を、A1より深く。
C2planned Bの指標をTwentyに落とし込む設計演習 B1〜B5それぞれに必要なフィールド・オブジェクトを、実際にTwenty上でどう作るか。
C3planned 要件ヒアリングの進め方 クライアントから要件を引き出す質問の型。このコースで得た語彙をヒアリングにどう使うか。
