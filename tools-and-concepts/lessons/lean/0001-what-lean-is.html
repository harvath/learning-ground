What Lean is

A working definition you can repeat to a colleague, and one eight-line example that shows the whole idea. No history, no theory yet.

The 30-second version

Lean is a programming language whose compiler can check mathematical proofs. You can use it like any functional language — define functions, run them, ship a binary. But in the same file, in the same language, you can also write down a precise claim ("this function always returns an even number", "there are infinitely many primes") together with a proof of it, and the compiler will refuse to build unless the proof is actually valid. Not "passes the tests" — valid, for every possible input, with no step skipped.

The general name for this kind of tool is a proof assistant (also "interactive theorem prover"): software that doesn't find proofs for you, but checks the ones you write, step by step, and tells you exactly what remains to be shown. Lean is one of several proof assistants. It's the one people are talking about, and lessons 4–7 are about why.

The whole idea in eight lines

-- 1. An ordinary function
def double (n : Nat) : Nat := n + n

-- 2. Run it
#eval double 21        -- 42

-- 3. A claim about it, and a proof
theorem double_eq (n : Nat) : double n = 2 * n := by
  unfold double
  omega

Valid Lean 4. Nat is the type of natural numbers: 0, 1, 2, …

Part 1 is a function definition that would look at home in Haskell, Scala, or Swift. Part 2 evaluates it.

Part 3 is the new thing. Read it as: "Theorem, named double_eq: for any natural number n, double n equals 2 * n." Everything after := by is the proof, written as two instructions: unfold double ("replace double n with its definition, n + n") and omega ("this is now simple integer arithmetic — finish it"). These instructions are called tactics: commands that transform what's left to prove until nothing is left.

Why that isn't just a unit test

A testA Lean theorem
What it saysdouble(21) == 42double n = 2 * n, for every n
What it coversThe inputs you thought ofAll inputs — infinitely many
When it's checkedWhen the test suite runsAt compile time, every build
If it's wrongMay pass anywayThe file does not compile

Change the theorem to claim double n = 3 * n and Lean rejects the file: omega reports it cannot prove the goal, because the claim is false. There is no way to talk it into accepting. That property — a false statement cannot get through — is the entire value of the tool.

"Interactive" is meant literally

You don't write a proof blind and submit it. In the editor, as your cursor moves through a proof, a side panel shows the current goal — what remains to be proved at that exact point. After unfold double the panel shows n + n = 2 * n; after omega it shows no goals left. Writing a proof feels less like writing an essay and more like stepping through a debugger until the stack is empty.

The same tool does serious mathematics

Nothing in that example is specific to programs. A theorem can just as well be about prime numbers, geometry, or infinite-dimensional spaces — the statement is written in the same language and the proof is checked by the same compiler. That's what makes Lean interesting to two audiences who normally share nothing: software people who want code proved correct, and mathematicians who want proofs checked by something more reliable than a tired referee.

Basic facts

Lean was created by Leonardo de Moura, who started it in 2013 while at Microsoft Research.[1] The current version, Lean 4, was officially released on September 8, 2023,[2] and is a ground-up rewrite — in Lean itself.[3] It is open source, and since July 2023 its development has been led by a dedicated non-profit, the Lean FRO.[1] (FRO stands for "Focused Research Organization" — more in lesson 4.)

Check it sticks

① Without looking: what is Lean, in one or two sentences, to an engineer who's never heard of it?

A programming language whose compiler can also check mathematical proofs. You write ordinary functional code, and alongside it precise claims plus proofs; the build fails unless every proof is valid — for all inputs, not only tested ones.

② What does a proof assistant like Lean do?

The human (or, as lesson 7 will show, an AI) supplies the proof; Lean checks it. Some tactics, like omega, automate narrow classes of steps, but there's no general "prove this for me" button. And it isn't testing — nothing is sampled.

③ In the example, what are unfold double and omega?

Tactics run at compile time and exist only to build the proof. unfold expands a definition; omega closes goals that are linear arithmetic over integers and naturals.
