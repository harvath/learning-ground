UNIT B · THE TECHNOLOGY STACK — LESSON 0009

Before a model can use data, someone has to build it

B3 covers how a model reaches data. This lesson is one level below that: how the data gets modeled, validated, and traced in the first place — the part most AI discussions skip entirely.

dbt — what it actually is, mechanically

dbt ("data build tool") is a command-line tool, not a language — it doesn't replace SQL, it wraps a thin templating layer (Jinja, for variables/loops/conditionals) around plain SQL SELECT statements. A model in dbt is just a .sql file containing one such statement; dbt's only real job is to compile that file into raw SQL and hand it to the warehouse (Snowflake, BigQuery, Databricks, etc.) to actually run — dbt itself does no data processing, all the compute stays in the warehouse.[1]

a concrete example Raw warehouse data might be a raw.customers table straight from your production database — messy column names, soft-deleted rows still present, no dedup. A dbt model stg_customers.sql might read: SELECT customer_id, first_name, email FROM source('raw', 'customers') WHERE deleted_at IS NULL — a plain SELECT, with one Jinja function (source(), normally written wrapped in double curly braces) marking where the raw table lives. A second model can then build on the first via ref('stg_customers') instead of hardcoding a table name — dbt uses every one of these ref() calls across a project to build a dependency graph (a DAG) and figure out what order to run models in, and re-run only what actually changed. That chain of small, testable, git-versioned SELECT statements — not one giant query — is what "modeling raw data into clean, reusable tables" means in practice. dbt also ships built-in tests you attach in YAML (e.g. a column must be unique or not_null) that run automatically and fail the build if violated, plus auto-generated documentation of the whole DAG.

dbt Core is the free, open-source CLI described above — you run it yourself, on a schedule you set up. dbt Cloud (now folded into the merged company's "dbt Platform," below) is the paid, hosted layer on top: scheduling, CI/CD, a browser IDE, hosted documentation, alerting. The open-source Core is what made dbt the de facto standard; the Cloud layer is dbt Labs' (now the merged company's) actual business model.

On adoption: as of a February 2025 company announcement, roughly 50,000 teams were running dbt every week, with 5,000+ paying dbt Cloud customers (30% year-over-year growth) and 85% year-over-year growth specifically in Fortune 500 adoption — the company crossed $100M in annual recurring revenue that month, up from $2M four years earlier.[2] However you weight "de facto standard," these are the underlying numbers behind that claim — and, per the merger below, note it's not a static picture even between last year and now.

dbt and Fivetran — now one company, and it changes the pitch

In 2026 dbt's story stopped being a standalone one: dbt Labs merged with Fivetran (a data-integration company) in an all-stock deal announced October 2025 and completed June 1, 2026. Fivetran's CEO George Fraser leads the combined company; dbt's CEO Tristan Handy becomes co-founder/President. Combined ARR was roughly $600M at announcement, valuing the merged entity at $9.8B.[3]

The merger's own branding is explicit about why: "the Data Infrastructure for Trusted AI Agents," not a BI consolidation play.[3] Concretely, this shows up as: Agents Schema, an open standard storing semantic models, metric definitions, dbt lineage, and business documentation as plain SQL tables in the warehouse — a "customer-owned context layer" any SQL-capable agent can read, reducing retrieval hops and avoiding vendor lock-in; dbt Agents, built on top of dbt and exposed via a dbt MCP server (B3's MCP, now showing up here too), turning structured dbt context into auditable actions; and dbt Fusion Engine, a new transformation engine that skips re-running unchanged models specifically to control AI-pipeline compute cost.[4]

Great Expectations — split in two directions at once

Great Expectations (GX) is a data-validation framework — you write "Expectations" (assertions like "this column is never null") and it checks incoming data against them before anything downstream trusts it. In 2026 it split into two separate stories, which is worth getting precisely right rather than glossing over: FICO acquired GX Cloud (the commercial SaaS product) and folded it into FICO's own AI-decisioning platform — GX Cloud stopped being publicly available June 1, 2026. Meanwhile, Fivetran became the new steward of the open-source GX Core framework — the same Fivetran from the dbt merger above.[5]

don't trust stale knowledge — a clean example Within a few months of each other in 2025–2026, Fivetran ended up stewarding both major open-source data-tooling projects in this space: dbt (via the full merger) and GX Core (via the FICO-acquisition side deal). Anyone still describing dbt Labs and Great Expectations as separate, unrelated companies — which was accurate as recently as 2024 — is working from an out-of-date picture. This is exactly the kind of fast-moving consolidation this course's whole premise is built around.

Before the split, GX had already shipped ExpectAI — AI-assisted generation of data-quality Expectations from profiling and business context, with a bring-your-own-credentials mode specifically built for "Agent deployments" where data never leaves the customer's environment, aimed at regulated industries (financial services, healthcare, automotive).[6]

OpenLineage and Marquez — the project came first, the standard came after

Here the intuitive assumption (a spec exists, then a reference implementation follows) runs backwards from what actually happened. Marquez — a metadata service for tracking data-pipeline lineage — was built by Willy Lulciuc and Julien Le Dem at WeWork starting in 2017 and open-sourced in 2019. OpenLineage, the open specification for what lineage events should look like, was created afterward, standardizing the API that Marquez had already built.[7] Both are now graduated projects under the Linux Foundation AI & Data Foundation — OpenLineage graduated July 2023, Marquez separately, though the two remain tightly coupled (Marquez is still effectively OpenLineage's reference implementation).[8]

a concrete example — what's actually inside a lineage event A lineage event is a small JSON object, not a document or a diagram. Every tool that supports OpenLineage (dbt, Spark, Airflow, Flink...) emits one whenever a job run starts and another when it finishes — at minimum a START and a COMPLETE/FAIL/ABORT event per run.[9] A trimmed COMPLETE event looks like: {"eventType":"COMPLETE","run":{"runId":"3b45..."},"job":{"namespace":"warehouse-etl","name":"stg_customers"},"inputs":[{"namespace":"warehouse","name":"raw.customers"}],"outputs":[{"namespace":"warehouse","name":"analytics.stg_customers"}]} — it names which job ran, a unique run ID, which dataset(s) it read (inputs), and which it wrote (outputs), each dataset identified by namespace+name. Extra metadata (column schema, row count, timing) rides along as facets — named, independently-versioned chunks of metadata attached to a job, run, or dataset (a schema facet lists columns and types; an outputStatistics facet gives row count and byte size).[10] A lineage graph — the thing Marquez actually renders — isn't one event, it's thousands of these events stitched together: if one job's output dataset name matches another job's input dataset name, that's an edge in the graph. No inference, no AI — just consistent naming carried across every tool's emitted events.
precision matters here: the spec vs. what's built on it You'll see "lineage tracing lets you audit what data an AI agent's decision was based on" as a 2026 selling point — real, but it's happening one layer above OpenLineage itself. The concrete example is Atlan, a commercial data-catalog company whose MCP server lets an AI agent query a lineage graph before using a column of data, returning provenance, transformation history, quality checks, and ownership in one call.[11] OpenLineage's own specification has not, as far as can be confirmed, been formally extended with agent-specific fields — the "lineage for agent governance" story is being built by vendors consuming OpenLineage events, not by the standard itself evolving. Worth keeping that distinction sharp rather than crediting the spec with a capability that actually lives one layer up.

Check it sticks

① As of mid-2026, which company controls both dbt and the open-source Great Expectations Core framework, and via what two different deals?

Fivetran. It fully merged with dbt Labs (announced Oct 2025, completed June 2026). Separately, it became the new steward of the open-source GX Core project as part of the deal in which FICO acquired the commercial GX Cloud product — a different, parallel transaction happening around the same time.

② Which came first: the OpenLineage specification, or Marquez (its reference implementation)?

Marquez came first (WeWork, 2017, open-sourced 2019). OpenLineage was created afterward as the open specification standardizing the lineage-event API that Marquez had already built — the reverse order of what "a spec and its reference implementation" usually implies.
