Where Lean sits: TLA+, Dafny, and the other neighbours

Conversations about Lean keep naming other tools — TLA+, Z3, Dafny, Verus, Kani, F*, Agda. This lesson is the map: what each one is, and the two questions that tell you which neighbourhood it lives in.

The 30-second version

Lean belongs to a wider family usually called formal methods: tools that use mathematics, rather than running examples, to show software does what it should. They differ on two questions.

What is being checked — a simplified model of the design, or the actual code? And who does the proving — a tool, automatically, within limits; or a person (or AI) guiding a proof step by step, without limits?

Lean's answer is the most demanding on both: it can check anything you can state, including the real code, with a guided proof and a tiny trusted kernel. Its neighbours each give up part of that in exchange for being much cheaper to use. That trade is why they exist, and why most industrial verification so far has been done with them rather than with a proof assistant.

1. TLA+ and model checking: check the design, not the code

TLA+ is a language created by Leslie Lamport for "writing precise high-level models of what code does and how it does it."[1] You don't write your system in it. You write a short description of the design — the possible states and the allowed steps between them, essentially a state machine — plus the properties that must always hold ("two nodes never both believe they're the leader").

Then a model checker takes over. Model checking means checking a finite-state model against a specification by exploring its states exhaustively.[2] As one practitioner puts it: "Instead of writing a proof that a design is correct, we just brute force the state space."[3] TLA+'s standard checker, TLC, tries every interleaving of every step for a small configuration (say, three nodes and two messages), and if a property can be violated it hands you the exact sequence of events that does it.

That last part is why engineers like it. The best-known evidence is from Amazon: by 2014, AWS teams had used TLA+ on core systems including S3, DynamoDB, and EBS, and it found bugs in each. One DynamoDB bug could lose data and needed a trace of 35 steps to trigger — far beyond what testing or design review would find.[4][5] Its siblings: P, used at AWS on the protocols behind S3's strong consistency,[6] and Alloy from MIT.[7]

TLA+ versus Lean in one breath TLA+ with a model checker: push-button, finds real design bugs in days, but checks a model at small sizes — it doesn't prove the design correct for every size, and it says nothing about whether your code matches the model. Lean: can prove a property for all sizes, about the real code — and you have to write the proof. Different jobs. Asking "TLA+ or Lean?" is usually a sign the problem hasn't been stated yet.

2. SMT solvers: the engine under the hood

An SMT solver (lesson 4 mentioned them) is a program that takes a logical formula involving things like integers, arrays, and bit-vectors and decides, automatically, whether it can be satisfied.[8] "SMT" stands for satisfiability modulo theories. You rarely use one directly. They sit underneath other tools: you'll hear Z3 (Microsoft Research)[9] and cvc5.[10]

The connection to Lean is personal: Z3's main architect was Leonardo de Moura, before he built Lean. He made the best-known tool of the fully-automatic school, then went and built one from the other school.

The strength of a solver is that there's nothing to write. The weaknesses: it only handles certain kinds of formula; when it fails it mostly just fails or times out, with little to tell you why; and you are trusting a large, complex program — the opposite of lesson 2's small kernel.

3. Dafny, Verus, Kani: real code, mostly automatic

The next neighbourhood applies solvers to actual programs. Dafny, created by Rustan Leino at Microsoft Research in 2009,[11] calls itself "a verification-aware programming language".[12] You write ordinary-looking imperative code and annotate it — this function requires x > 0; it ensures the result is sorted; this loop keeps this invariant — and the tool turns code plus annotations into formulas for Z3. If the solver is satisfied, the code meets its spec. No proof script. Dafny then compiles to C#, Java, JavaScript, Go, or Python.[12]

It runs in production at scale: AWS rewrote its authorization engine — the code that decides whether each API call is allowed, invoked a billion times per second — in Dafny, and deployed it in 2024.[13]

The same approach for Rust: Verus verifies Rust code using Z3,[14] and Kani is a model checker for Rust that examines the code itself rather than a design.[15] There's an ongoing AWS-initiated effort to verify the Rust standard library this way.[16] And F*, also from Microsoft Research, is the language behind HACL*, the verified cryptography library shipped in Firefox and the Linux kernel.[17]

The trade against Lean is the solver's trade: far less work per line of code when it goes through, and little recourse when it doesn't. A proof that passed yesterday can time out today after an unrelated change. In Lean a proof is longer to write, but it's an explicit artifact that either checks or doesn't, the same way every time.

4. The other proof assistants, and two cousins

Rocq (formerly Coq) and Isabelle, from lesson 3, are Lean's direct peers and remain in active use. Two more names come up from the programming-language side: Agda and Idris. Both are dependently typed languages built on the same propositions-as-types idea as Lean (lesson 2). Their emphasis is on programming and type-theory research — Agda has no separate tactic language at all, proofs are written directly as programs[18] — and neither has anything like mathlib. If someone says "Lean is like Agda or Idris", they mean the type system; if they say "Lean is like Coq", they mean the whole proof-assistant package.

The borders are blurring

Three developments make this map less tidy than the table suggests, and they're where much of today's Lean-for-software discussion happens.

Solver-style automation is moving inside Lean. Lean's grind tactic "uses techniques inspired by modern SMT solvers to automatically construct proofs" — but, unlike a solver, it "produces ordinary Lean proof terms", so the kernel still checks the result.[19] That's the omega pattern from lesson 1, generalized: automation you don't have to trust.

Real code is being translated into Lean. Aeneas converts Rust programs into Lean so they can be reasoned about there.[20] This is how one proves things about code that wasn't written in Lean.

Projects move between neighbourhoods. Amazon's Cedar policy language was first modelled in Dafny (2023);[21] its models and proofs are now in Lean.[22]

And AI changes the trade

The whole map is drawn around one cost: human proof effort. Tools gave up assurance to save it. If AI can write the proofs, that cost drops, and the question becomes which target is best for a machine.

It isn't settled. A September 2025 benchmark gave the same kind of task — write code and prove it meets a spec — to off-the-shelf language models in three languages. Success rates: Dafny 82%, Verus 44%, Lean 27%.[23] Sept 2025 — will have moved The push-button tools were the easier target. Yet for mathematics, AI work converged on Lean almost entirely. De Moura's explanation (he's an interested party) is the small kernel, the size of mathlib, and the fact that an interactive prover gives a model feedback after every step, where a solver only says pass or fail.[24] There's AI work on TLA+ too — a 2025 challenge was won by a tool that derives TLA+ specs from source code.[25]

rule of thumb Designing a concurrent or distributed protocol? Model it in TLA+ or P first — cheapest, and it finds the bugs that matter most.
Want a specific module proved correct with the least effort? A verification-aware language or code verifier: Dafny, Verus, Kani.
Need a property no solver will prove on its own, real mathematics, or the smallest possible thing to trust? A proof assistant — and today, most likely Lean.
Not there yet? Property-based testing, fuzzing, and deterministic simulation are the same instinct at a fraction of the cost, and where most teams should start.

Check it sticks

① What are the two questions that place any formal-methods tool on the map?

(1) What is being checked — a model of the design, or the actual code? (2) Who does the proving — a tool automatically, within limits, or a person or AI guiding the proof step by step? TLA+ is model + automatic; Dafny/Verus are code + mostly automatic; Lean is anything + guided.

② Your team's TLA+ spec of a replication protocol passes the model checker. What do you know?

Model checking explores a model at bounded sizes. That's valuable — it's how AWS found a 35-step data-loss bug — but it isn't a statement about the code, and it isn't a proof for all sizes. Both of those need other tools.

③ What is the main thing Dafny gives up compared with Lean, in exchange for being much less work?

Dafny checks real code and compiles to several mainstream languages. Its limits are the solver's limits: narrower reach, opaque failures and timeouts, and a big trusted component instead of a small kernel.

④ How is Lean's grind tactic different from calling an SMT solver directly?

Same trust model as every other tactic (lesson 2): anything may generate the proof, the kernel decides. That's how Lean gets some of the neighbours' convenience without their larger trusted base.
