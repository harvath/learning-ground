The idea underneath: propositions are types

How a compiler can check a proof — and why you only have to trust a very small part of it. This is the one concept lesson in the set; everything else is story.

The 30-second version

You already trust a type checker to verify small claims. When a function is declared to return an Int and the code compiles, the compiler has proved a little theorem: "this code always produces an integer." Lean's idea is to make the type system expressive enough that a type can state any precise claim — "double n equals 2 * n", "there is no largest prime". Then:

A statement is a type. A proof of the statement is a value of that type. Checking a proof is type-checking.

That's it. Lean has no separate "proof checker" bolted onto a language. The proof checker is the type checker.

Climbing up to it

Nat
A plain type. Its values: 0, 1, 2, …
List Nat
A type built from another type — generics, as in most languages.
Vector Nat 3
"Lists of naturals of length exactly 3." A type that mentions a value (the 3). This is a dependent type — a type that depends on a value — and most mainstream languages can't express it. Passing a length-2 vector here is a compile error.
2 + 2 = 4
Once types can mention values, this is a type too. Its values are the proofs that 2 + 2 is 4. Likewise 2 + 2 = 5 is a perfectly legal type — it just has no values, so you can never construct one.

A proposition is just a statement that might be true or false. In Lean, a true proposition is a type you can produce a value of; a false one is a type that's empty. "Proving a theorem" means "writing an expression that has that type".

Proofs really are programs

-- "If p and q are both true, then q and p are both true."
theorem and_swap (p q : Prop) (h : p ∧ q) : q ∧ p :=
  ⟨h.2, h.1⟩

∧ means "and". Prop is the type of propositions. ⟨a, b⟩ builds a pair.

Look at what the proof is. A proof of "p and q" is a pair: a proof of p together with a proof of q. So and_swap is a function that takes a pair h and returns the pair with its two components swapped. It's the same code you'd write to swap a tuple — and because it type-checks, the logical claim is proved.

The dictionary extends to all of logic:

In logicIn programming
A propositionA type
A proofA value (a program) of that type
"p and q"A pair of a p and a q
"p implies q"A function from p to q
"for every n, P(n)"A function that takes n and returns a proof of P(n)
Checking a proofType-checking the program

This correspondence wasn't invented for Lean. It's known as the Curry–Howard correspondence — observed by the logician Haskell Curry in 1934 and extended by William Howard in 1969 — and is often summarized as "propositions as types, proofs as programs".[1] The particular type system Lean uses is a version of the "Calculus of Constructions", one member of the family called dependent type theory.[2] You don't need either name to use the idea; you do need them to read anything else about Lean.

Where tactics fit

Writing proofs directly as expressions works for and_swap and becomes unbearable for real mathematics. That's what the tactics from lesson 1 are for. A by block is a small script that generates the proof expression for you: omega ran an arithmetic procedure and emitted a (large, unreadable) expression of the right type. You never see it. But it exists, and it gets type-checked like everything else.

Why this makes Lean trustworthy: the kernel

Here is the design consequence that matters most for the rest of this set. Lean is a big system — parser, tactics, automation, editor integration — and big systems have bugs. But no matter how a proof was produced, by hand, by a tactic, by a buggy tactic, by an AI, the end product is always the same kind of thing: a proof expression. And that expression is re-checked by one small component, the kernel: in the documentation's words, "a small, robust implementation of a type checker for the core type theory."[3]

the trust model Everything outside the kernel is untrusted. A tactic with a bug can fail to find a proof, or produce a broken one — and the kernel will reject it. To believe a Lean theorem you don't need to trust the person, the tactics, or the tool that wrote the proof. You need to trust the kernel, and the statement of the theorem.

If you know cryptography or complexity theory, you've seen this shape: finding a solution is hard and can be done by anyone, however unreliable; verifying a solution is easy and is done by a small trusted checker. Verifying a signature doesn't require trusting whoever handed it to you.

The principle is older than Lean. It's called the de Bruijn criterion, after N.G. de Bruijn, whose Automath project (begun 1967) first made a point of it: a proof assistant should produce a proof object checkable by a program simple enough that "a skeptic user could easily write him/herself."[4] People have done exactly that for Lean — there are independent re-implementations of its kernel, in Rust and in Lean itself, so one checker's bug is unlikely to be shared by the others.[3] (Lesson 7 looks at what happened when that assumption was tested.)

Check it sticks

① Complete the three-part slogan: "A statement is a ___. A proof is a ___. Checking a proof is ___."

A statement is a type. A proof is a value (program) of that type. Checking a proof is type-checking. A false statement is a type with no values, which is why no proof of it can be written.

② Under propositions-as-types, a proof of "p implies q" is…

Implication is a function type. The pair is "p and q". And proofs aren't booleans computed at runtime — they're values whose mere existence, confirmed by the type checker, establishes the claim.

③ A widely used tactic turns out to have a serious bug. What's the worst that can happen to theorems already proved with it?

Tactics are outside the trusted core. A buggy tactic can fail, or produce garbage that the kernel refuses; it can't make the kernel accept a false statement. Only a bug in the kernel itself could do that — which is why the kernel is kept small.

④ In your own words: what is the de Bruijn criterion, and why does it matter if an AI is writing the proofs?

A proof assistant should output proofs that a small, simple, independent program can check — so trust rests on that small checker, not on the big system. It matters for AI because the proof's author no longer needs to be trusted at all: however the proof was generated, it either passes the kernel or it doesn't. (This is the heart of lesson 6.)
